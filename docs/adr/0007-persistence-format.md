# ADR-0007: 台帳を移動の行で、相談とおねがいをようすとイベントで保存する

## Status

Proposed

## Date

2026-10-03

## Context

ADR-0005 で多通貨の複式の台帳を、ADR-0006 で PostgreSQL、pgx、sqlc、goose を採用した。また、`docs/domain/` にドメインの仕様をまとめた。これらを PostgreSQL のテーブルとしてどう保存するかを決める必要がある。

保存の形式には、次の要件がある。

- P1: 台帳の取引の金額の合計が、通貨ごとに 0 であることを保証する（ADR-0005）。
- P2: 台帳の記録と、相談やおねがいのイベントを、更新・削除できないようにする（ADR-0005）。
- P3: いいね待ちの相談の一覧など、相談やおねがいの今のようすで素早く検索できる。
- P4: 誰が、いつ、相談やおねがいのようすを変えたかを辿れる。
- P5: ようすごとに持つデータ（いいね済みの期限、見送りの理由など）が、そのようすのときだけ存在する。
- P6: 同じ相談に、複数のおさいふ係が同時にいいねや見送りをしても、正しく 1 つずつ扱われる。
- P7: 同じおうちの複数の相談にいいねがそろうとき、やりくりの残りを早いもの勝ちで正しく判断する（`docs/domain/like.md`）。
- P8: 相談のようすの変更、イベントの追記、台帳の記録を、まとめて書き込むか、まとめて失敗させられる。
- P9: 将来、イベントをメッセージブローカーに送るとき、データベースへの保存とブローカーへの送信が食い違わない。
- P10: 今月のやりくり、どきどきライン、おうちの時間、おうちのお金の、過去の値を求められる（`docs/domain/budget.md`、`docs/domain/household.md`）。

## Options Considered

### 台帳の保存

#### Option 1: 符号付きの記録の行

- 概要: 勘定ごとの符号付きの金額を 1 行ずつ保存し、合計が 0 であることを、トランザクションの終わりに遅延の制約トリガーで検証する。
- 利点: ADR-0005 の記録の表し方をそのまま保存できる。
- 欠点: 合計が 0 でない取引を一度作ってから拒否する、検証による保証になる。トリガーと関数の管理が必要になる。

#### Option 2: 移動の行

- 概要: 「移動元の勘定、移動先の勘定、金額、通貨」を 1 行として保存する。金額は常に正とする。
- 利点: 1 行の中で出ていく金額と入る金額が同じ値なので、どんな値を入れても通貨ごとの合計が 0 になり、合計が 0 でない取引をそもそも表現できない。トリガーが要らない。通貨ごとに合計が 0 になる記録の組は、必ず移動の組に分解できるため、表現できる取引の範囲は Option 1 と変わらない。
- 欠点: ADR-0005 の符号付きの記録と、保存の形が異なるため、変換が必要になる。

### 相談とおねがいの保存

#### Option 1: 今のようすのテーブルだけ

- 概要: ようすの列を持つ行を、ようすが変わるたびに更新する。
- 利点: 最も単純で、検索しやすい（P3）。
- 欠点: 更新した時点で以前のようすが失われ、経緯を辿れない（P4）。

#### Option 2: イベントソーシング

- 概要: イベントだけを追記し、今のようすはイベントから導出する。
- 利点: 経緯を完全に辿れる（P4）。今のようすがイベントの列を畳み込む純粋な関数の結果になる。
- 欠点: 今のようすで検索するには、検索用のテーブルを別に作って最新に保つ必要があり（P3）、その管理が FP の検証とは別の負担になる。

#### Option 3: 今のようすのテーブルと、イベントのテーブルの併用

- 概要: 今のようすのテーブルと、追記専用のイベントのテーブルの両方を持ち、ようすを変えるときは同じトランザクションで両方に書き込む。
- 利点: 検索しやすさ（P3）と、経緯の辿りやすさ（P4）を両立できる。ドメインのロジックは、イベントソーシングと同じ「決める関数」と「適用する関数」の形で書ける。
- 欠点: 2 つのテーブルが食い違わないよう、書き込みを 1 か所にまとめ、テストで検証する必要がある。

### メッセージングへの備え

#### Option 1: 保存のあとに、ブローカーへ直接送る

- 概要: データベースに保存したあと、アプリケーションがブローカーにイベントを送る。
- 利点: 仕組みが単純である。
- 欠点: 保存と送信の片方だけが成功すると、データと通知が食い違う（P9）。

#### Option 2: イベントのテーブルをアウトボックスとして使う

- 概要: イベントのテーブルを、送信待ちのイベントの置き場所としても使い、別の仕組みがそれを読んでブローカーに送る。
- 利点: イベントは状態の変更と同じトランザクションで保存されるため、保存と送信が食い違わない（P9）。今はブローカーを導入せず、必要になったときに送る仕組みを足すだけで済む。
- 欠点: 送信済みかどうかを管理する仕組みが、将来必要になる。

### 同時の操作の制御

#### Option 1: 直列化可能な分離レベル

- 概要: トランザクションの分離レベルを `SERIALIZABLE` にし、競合したトランザクションをやり直す。
- 利点: 競合を漏れなく検出できる。
- 欠点: 競合のたびにやり直しの処理が必要になり、どの操作が競合しうるかが見えにくい。

#### Option 2: おうちの行のロックと、バージョンによる楽観的ロック

- 概要: やりくりの残りを判断する操作では、おうちの行を `SELECT ... FOR UPDATE` でロックして、同じおうちの操作を 1 つずつ順に扱う。同じ相談やおねがいへの同時の操作は、バージョンによる楽観的ロックと、イベントのテーブルの一意制約で防ぐ。
- 利点: どの操作がどのように直列になるかが、コードから明確に分かる。同じおうちの中で操作が同時に起きる頻度は低く、直列にしても性能の問題になりにくい。
- 欠点: ロックを取り忘れると、早いもの勝ちが正しく働かない。

## Decision

### 台帳

- 台帳は、移動の行として保存する（台帳の保存の Option 2）。
- 移動の行には、CHECK 制約で「金額は正である」「移動元と移動先は異なる勘定である」を課す。
- 移動の行は、それを生じさせたイベント、またはたてかえのおかえしを参照する。

### 相談とおねがい

- 相談とおねがいは、今のようすのテーブルと、イベントのテーブルの併用で保存する（相談とおねがいの保存の Option 3）。
- ようすを変えるときは、ドメインの「決める関数」で得たイベントを「適用する関数」で今のようすに適用し、新しいようすとイベントを同じトランザクションで保存する。
- ようすごとに持つデータが、そのようすのときだけ存在することを、ようすのテーブルの CHECK 制約で保証する。買った金額が相談した金額以下であることも、CHECK 制約で保証する。
- いいねは、相談やおねがいといいねした家族の組を一意とし、同じ家族が 2 回いいねすることをデータベースでも拒否する。

### イベントのテーブル

- 相談、おねがいなど、すべてのイベントを 1 つのイベントのテーブルに保存する。どの相談やおねがいのイベントかは、種類と ID の組で表す。
- イベントは、`docs/domain/consultation.md` の「すべてのイベントが持つもの」を列として持ち、種類ごとに異なる内容は JSONB の列に、内容の形のバージョンとともに保存する。
- 種類、ID、バージョンの組を一意とする。
- イベントのテーブルを、将来のメッセージングのアウトボックスとして使う（メッセージングへの備えの Option 2）。今はブローカーを導入しない。
- 時間切れは、記録した報告の期限と今の時刻から判断できるため、イベントとして記録しない。

### おうちの設定の履歴

- 今月のやりくり、どきどきライン、おうちの時間、おうちのお金は、いつから有効になったかを持つ追記専用の履歴のテーブルに保存し、更新しない。過去の値は、履歴から求める。
- 履歴の行は、それを生じさせたおねがいのイベントを参照する。

### 同時の操作の制御

- 同時の操作は、おうちの行のロックと、バージョンによる楽観的ロックで制御する（同時の操作の制御の Option 2）。
- やりくりの残りを判断する操作（相談の 1 つ目のいいね、いいねがそろうとき）では、おうちの行を `SELECT ... FOR UPDATE` でロックする。
- 相談やおねがいのようすを更新するときは、読み込んだときのバージョンを条件にし、更新した行が 0 件なら、ほかの操作が先に行われたものとしてエラーにする。

### 更新・削除の禁止

- アプリケーションが使うデータベースのロールには、台帳の移動の行のテーブル、イベントのテーブル、おうちの設定の履歴のテーブルについて、`SELECT` と `INSERT` の権限だけを与える。権限の付与は goose のマイグレーションで行う。
- `sqlc vet` で、これらのテーブルに対する `UPDATE` と `DELETE` のクエリを禁止する。

### Tradeoffs

台帳の合計が 0 であることを構造で保証できること、今のようすでの検索と経緯の辿りやすさを両立できること、将来のメッセージングに保存の形を変えずに移行できることを得る代わりに、ドメインの符号付きの記録と保存の形の変換、ようすとイベントの 2 つのテーブルへの書き込みの管理、ロックを取る操作の明示を受け入れる。

### Confidence

Medium

台帳の移動の行と、ようすとイベントの併用は、それぞれ確立した方式である。ただし、これらを組み合わせた相談の一連の流れ（いいね、早いもの勝ち、買ったよ報告、台帳の記録）は、まだ実装していない。相談の流れを最初から最後まで実装した時点で、テーブルの構成とロックの範囲を見直す。

## Consequences

### Positive

- 台帳の取引の合計が通貨ごとに 0 であることを、トリガーなしに構造で保証できる。
- 相談やおねがいを、今のようすで検索でき、誰がいつようすを変えたかも辿れる。
- ようすごとのデータの組み合わせの誤りを、データベースが拒否する。
- イベントのテーブルがアウトボックスを兼ねるため、将来メッセージングを導入するときに保存の形を変えずに済む。
- 台帳、イベント、設定の履歴を更新・削除できないことを、データベースの権限と `sqlc vet` の 2 段階で守れる。

### Negative

- ドメインの符号付きの記録と、保存の移動の行の間で、変換が必要になる。
- ようすのテーブルとイベントのテーブルが食い違わないよう、書き込みを 1 か所にまとめる必要がある。
- イベントの内容を JSONB に保存するため、内容の形を変えるときは、古い形のイベントを読み分ける処理が必要になる。
- ロックを取る操作を明示的に書く必要があり、取り忘れると早いもの勝ちが正しく働かない。

## Compliance

- 台帳の残高を求める関数について、移動の行から求めた各勘定の残高の合計が、通貨ごとに 0 になることをテストする。
- 相談とおねがいについて、すべてのイベントを最初から適用した結果が、保存された今のようすと一致することをテストする。
- 同じ相談に同時にいいねした場合と、同じおうちの複数の相談に同時にいいねがそろった場合のテストを、実際の PostgreSQL に対して行う。
- マイグレーションで、アプリケーションのロールに台帳、イベント、設定の履歴のテーブルの `UPDATE` と `DELETE` の権限がないことを確認する。
- `sqlc vet` のルールを CI で実行する。
- 相談の流れを最初から最後まで実装した時点で、この ADR の Confidence を見直す。
