# ADR-0010: パスキーとおさいふ係の招待で認証し、セッションをサーバーで管理する

## Status

Accepted

## Date

2026-10-14

## Context

API を実装するには、バックエンドが「誰が操作しているか」を知る必要がある。このアプリの認証には、次の要件がある。

- A1: 子どもを含む家族全員が、迷わずログインできる。子どもはメールアドレスを持っていないことがある。
- A2: 家族を加えるのはおさいふ係の役割である（`docs/domain/household.md`）。
- A3: ログインする「アカウント」と、おうちの「家族」を分けて扱い、将来 1 人が複数のおうちに属せるようにする。
- A4: Web と、将来のモバイルアプリの両方で使える。
- A5: 家計を扱うため、パスワードの使い回しやフィッシングによるなりすましを防ぐ。
- A6: 認証は FP の検証の対象ではないため、暗号の処理を自分で書かず、実績のある仕組みに任せる。

## Options Considered

### Option 1: メールアドレスとパスワード

- 概要: メールアドレスとパスワードでログインする。
- 利点: 最も一般的で、利用者が慣れている。
- 欠点: パスワードの安全な保存と、忘れたときの再設定の仕組み（メールの送信を含む）を作る必要がある。子どもにパスワードを管理させるのが難しい（A1）。パスワードの使い回しやフィッシングに弱い（A5）。

### Option 2: メールのリンクでログインする

- 概要: メールで届くリンクを開いてログインする。
- 利点: パスワードが要らない。
- 欠点: メールを送る仕組みが必要で、メールアドレスのない子どもは使えない（A1）。

### Option 3: Google などの外部のアカウントでログインする

- 概要: OAuth / OpenID Connect で、外部のアカウントでログインする。
- 利点: パスワードの管理を外部に任せられる。
- 欠点: 子どもが外部のアカウントを持っているとは限らない（A1）。家族の情報を外部のサービスに結びつけることになる。

### Option 4: 認証サービスを使う

- 概要: Auth0、Clerk、Firebase Authentication などに、ログインの仕組みをまとめて任せる。
- 利点: ログインの画面や仕組みを作る手間が少なく、安全性も高い（A5、A6）。
- 欠点: 外部のサービスへの依存と費用が生まれる。子どもの登録や、おさいふ係が家族を招待する流れは、結局自分で組み立てる必要がある。

### Option 5: パスキーとおさいふ係の招待

- 概要: パスキー（WebAuthn）で、端末の指紋認証・顔認証・PIN でログインする。家族は、おさいふ係が作った招待から、自分の端末でパスキーを作る。
- 利点: パスワードもメールアドレスも要らず、子どもでも使える（A1）。フィッシングに強い（A5）。暗号の処理は実績のあるライブラリに任せられる（A6）。家族を加えるのはおさいふ係というドメインのルールが、そのまま認証の流れになる（A2）。
- 欠点: 端末をなくしたときの復旧を考える必要がある。登録とログインの画面の流れが、パスワードより複雑になる。

## Decision

Option 5 を採用し、パスキーとおさいふ係の招待で認証する。

### ログインの方法

- パスキー（WebAuthn）でログインする。WebAuthn の処理は、Go のライブラリ（go-webauthn）に任せる。
- おうちをつくる人は、最初の登録のときに、その端末でパスキーを作る。
- 家族を加えるときは、おさいふ係が招待を作る。招待は、1 回だけ使え、有効期限のあるコード（QR コードやリンクとしても渡せる）である。家族は自分の端末で招待を開き、パスキーを作る。
- 1 つのアカウントは、複数のパスキーを持てる。

### 復旧

- 家族が端末をなくしたときは、おさいふ係がその家族の招待をもう一度作り、新しい端末でパスキーを作り直す。
- なくした端末のパスキーとセッションは、無効にできるようにする。
- 唯一のおさいふ係がすべての端末をなくすと、復旧の手段がない。そのため、最初の登録のときに、別の端末にもパスキーを作ることや、端末の間で同期されるパスキーを使うことを案内する。MVP では、これ以外の復旧の手段は用意しない。

### セッション

- セッションはサーバーで管理する。ログインに成功したら、推測できないランダムな値をセッションの ID として発行し、データベースにはそのハッシュだけを保存する。
- Web では、セッションの ID を `HttpOnly`、`Secure`、`SameSite=Lax` の Cookie に入れる。状態を変えるリクエストでは、`Origin` のヘッダーも確かめる。
- 将来のモバイルアプリでは、同じセッションの ID を `Authorization` のヘッダーで送る。
- セッションには有効期限を設け、ログアウトや端末の紛失のときに、すぐに無効にできるようにする。具体的な期限の長さは、実装するときに決める。

### アカウントと家族

- ログインするアカウント（パスキーとセッションを持つ）と、おうちの家族（役割とようすを持つ）を、別のテーブルにする。
- 今は、1 つのアカウントは 1 つのおうちの家族にだけなれる、という制約を付ける。

### Tradeoffs

パスワードやメールアドレスなしに、子どもを含む家族全員が安全にログインでき、家族を加える流れとドメインのルールを一致させられることを得る代わりに、パスキーの登録とログインの画面の複雑さと、端末をなくしたときの復旧の設計を受け入れる。

### Confidence

Medium

パスキーは主要なブラウザと OS が対応した標準の仕組みであり、Go のライブラリも成熟している。一方で、パスキーの画面の流れと、招待による復旧の使い勝手は、実際に家族で使ってみないと分からない。最初のログインと招待を実装し、家族で試した時点で、この判断を見直す。

## Consequences

### Positive

- パスワードの保存、再設定、メールの送信の仕組みが要らない。
- フィッシングやパスワードの使い回しによるなりすましを防げる。
- 子どもは、指紋認証や顔認証だけでログインできる。
- セッションをすぐに無効にでき、端末の紛失に対応できる。
- アカウントと家族を分けておくことで、将来、複数のおうちに属せるようにする変更が小さく済む。

### Negative

- パスキーの登録とログインの画面の流れを、フロントエンドで実装する必要がある。
- 唯一のおさいふ係がすべての端末をなくすと、復旧の手段がない。
- 開発とテストでは、本物の認証器の代わりに、ブラウザの仮想の認証器を使う必要がある。
- セッションをデータベースで管理するため、リクエストのたびにセッションを確かめる処理が必要になる。

## Compliance

- セッションの ID と招待のコードは、データベースにはハッシュだけを保存する。
- セッションの Cookie に `HttpOnly`、`Secure`、`SameSite=Lax` が付いていることを、テストで確かめる。
- 招待のコードが 1 回しか使えないこと、有効期限を過ぎると使えないことを、テストで確かめる。
- 最初のログインと招待を実装し、家族で試した時点で、この ADR の Confidence を見直す。
