# ADR-0006: PostgreSQL、pgx、sqlc、goose で永続化する

## Status

Proposed

## Date

2026-10-03

## Context

バックエンドで家族、申請、カテゴリ、台帳などのデータを永続化するため、データベースと、Go からのアクセス方法、スキーマの変更を管理する方法を決める必要がある。

これまでの ADR とルールから、永続化には次の要件がある。

- D1: 1 つの取引の複数の記録を、まとめて書き込むか、まとめて失敗させられる（ADR-0005）。
- D2: 残高超過の判定で、並行した支払いが両方とも判定を通ってしまうことを防げる（ADR-0005）。
- D3: 台帳の記録の更新・削除を、データベースで禁止できる（ADR-0005）。
- D4: 参照されているカテゴリの削除を、データベースが拒否できる。
- D5: 64 ビットの整数で金額を持てる（ADR-0004）。
- D6: ドメインのルールの一部を、データベースのスキーマでも宣言的に表現できる。
- D7: ローカルの開発環境と CI で、同じデータベースを簡単に用意できる。
- D8: Go のコードで、実行される SQL が明示的で、結果が型付きで返り、状態や隠れたミューテーションがない（`docs/rules/backend.md` §2、§3、§5）。
- D9: 実務で広く使われている技術である。

台帳と申請の状態をどの形式で保存するかは、別の ADR で決める。

## Options Considered

### データベース

#### Option 1: PostgreSQL

- 概要: 汎用のリレーショナルデータベース。
- 利点: D1〜D5 をすべて満たす。部分インデックス、ドメイン型、CHECK 制約、排他制約など、ルールをスキーマで宣言的に書く仕組みが多い（D6）。スキーマの変更をトランザクションの中で実行でき、マイグレーションが途中で失敗してもデータベースが中途半端な状態に残らない。公式の Docker イメージがあり、CI のサービスコンテナとしても使いやすい（D7）。
- 欠点: 特になし。

#### Option 2: MySQL

- 概要: 汎用のリレーショナルデータベース。
- 利点: D1〜D5 を満たす。実務で広く使われている。
- 欠点: スキーマの変更が暗黙に確定されるため、マイグレーションが途中で失敗すると手で片付ける必要がある。制約をトランザクションの終わりまで遅延させる仕組みがない。

#### Option 3: SQLite

- 概要: アプリケーションに組み込むデータベース。
- 利点: 導入が最も手軽で、書き込みが直列に行われるため並行性の問題が起きにくい。
- 欠点: 各国の家族が使うサービスとして、複数のサーバーで運用する構成にしにくい。Web サービスのメインのデータベースとしては一般的とは言いにくい（D9）。

### アクセス方法

#### Option 1: 標準ライブラリとドライバーで手書きする

- 概要: `database/sql` や pgx で SQL を書き、結果を手で構造体に読み込む。
- 利点: SQL を完全に制御できる。
- 欠点: 結果を読み込むコードを毎回書く必要があり、列の数や型の不一致は実行するまで分からない。

#### Option 2: sqlc

- 概要: 手で書いた SQL から、型付きの Go の関数と構造体を生成する。
- 利点: 実行される SQL がそのまま残る。生成されるのは、引数を受け取って結果のデータを返す関数と、状態を持たない構造体だけで、データとそれを扱う関数が分かれている（D8）。クエリとスキーマの不整合をコードの生成時に検出できる。クエリに独自のルールで検査をかけられる（`sqlc vet`）。実行時に sqlc への依存が残らない。
- 欠点: 条件によって WHERE 句や並び順が変わる動的なクエリを書きにくい。

#### Option 3: ent

- 概要: スキーマを Go のコードで定義し、型付きのクエリビルダーを生成する ORM。
- 利点: 型の安全性が高く、リレーションを扱いやすい。実務で使われている。
- 欠点: 取得したエンティティをビルダーで変更して保存する形が中心で、状態を持つオブジェクトとミューテーションを前提とする。実行される SQL が ent の内部の振る舞いに隠れる。

#### Option 4: GORM

- 概要: リフレクションを使う ORM。
- 利点: 手軽に書け、利用者が多い。
- 欠点: 型の誤りが実行時まで分からない。関連の自動保存やゼロ値の扱いなど、暗黙の振る舞いが多い（D8）。

### マイグレーション

#### Option 1: goose

- 概要: SQL のファイルを順に実行するマイグレーションツール。
- 利点: マイグレーションは素の SQL なので、PostgreSQL のあらゆる機能を制限なく書ける。有料版による機能の制限がない。sqlc がマイグレーションのファイルから直接スキーマを読み取れるため、スキーマを二重に管理しなくてよい。
- 欠点: 望ましいスキーマとの差分の自動生成や、危険なスキーマの変更の検出がない。

#### Option 2: Atlas

- 概要: 望ましいスキーマを宣言し、現在のスキーマとの差分から変更を生成できるツール。
- 利点: 差分の自動生成、スキーマのずれの検出など、機能が豊富である。実務で使われている。
- 欠点: トリガー、関数、権限などのデータベースのオブジェクトの管理や、マイグレーションの検査は有料版の機能であり、無料版では使えない。

#### Option 3: golang-migrate

- 概要: SQL のファイルを順に実行するマイグレーションツール。
- 利点: goose と同様に単純で、広く使われている。
- 欠点: goose と比べて、開発中の番号の衝突を避ける運用の支援が少ない。

## Decision

データベースに PostgreSQL、ドライバーに pgx（v5）、アクセス方法に sqlc、マイグレーションに goose を採用する。

- PostgreSQL は、導入する時点の最新の安定版を使う。
- マイグレーションは goose の SQL のファイルで書き、Go のコードによるマイグレーションは使わない。
- sqlc は goose のマイグレーションのファイルからスキーマを読み取り、pgx（v5）向けのコードを生成する。
- sqlc が生成した型は、リポジトリの実装の中だけで使い、外にはドメインの型だけを返す。
- ローカルの開発環境では Docker Compose で PostgreSQL を起動し、CI では GitHub Actions のサービスコンテナで起動する。リポジトリのテストは、実際の PostgreSQL に対して実行する。

### Tradeoffs

実行される SQL が明示的で、状態を持たない関数とデータでデータベースにアクセスできることと、PostgreSQL の機能を制限なく使えることを得る代わりに、動的なクエリの書きにくさと、スキーマの差分の自動生成がないことを受け入れる。また、実務で使っている ent と Atlas とは異なるツールを使うため、この実験で得られた利点のうち、どこまでが FP の原則によるもので、どこまでが sqlc によるものかを切り分けて評価する必要がある。

### Confidence

High

PostgreSQL、pgx、sqlc、goose は、いずれも実務で広く使われている組み合わせである。家計の記録と集計は条件の組み合わせが限られており、sqlc の動的なクエリの書きにくさが大きな問題になる可能性は低い。

## Consequences

### Positive

- 実行される SQL が、クエリのファイルと Pull Request の差分にそのまま現れ、レビューしやすい。
- クエリとスキーマの不整合を、コードの生成時に検出できる。
- データベースへのアクセスが、状態を持たない関数の呼び出しとして明示的に表れる。
- PostgreSQL の制約をスキーマに宣言的に書き、ドメインのルールの一部をデータベースでも守れる。
- マイグレーションが途中で失敗しても、スキーマの変更は取り消される。

### Negative

- 動的なクエリは、省略可能な引数を使う書き方や、一部での手書きの SQL の併用で補う必要がある。
- スキーマの全体像は、マイグレーションのファイルを順に読むか、データベースから出力して確認する必要がある。
- 危険なスキーマの変更（長時間のロックを取るものなど）を自動で検出する仕組みがないため、必要になったら別の linter で補う。
- 実務で使っている ent と Atlas の経験を直接活かせない。実験の結果を ent の環境に持ち込むときは、sqlc に依存した利点を差し引いて評価する必要がある。

## Compliance

- sqlc が生成したコードはリポジトリにコミットし、CI でコードを生成し直して差分がないことを確認する。
- ドメイン層のパッケージが、sqlc が生成したパッケージと pgx を import しないことを、`depguard` で強制する。
- `sqlc vet` で、クエリに対するルール（台帳のテーブルへの `UPDATE` と `DELETE` の禁止など）を CI で検査する。具体的なルールは、台帳の保存形式を決める ADR で定める。
- マイグレーションは CI のサービスコンテナの PostgreSQL に適用し、適用に失敗しないことを確認する。
- 実験の振り返りの際に、得られた利点を「FP の原則によるもの」と「sqlc によるもの」に分けて記録する。
