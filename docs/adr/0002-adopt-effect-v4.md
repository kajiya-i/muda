# ADR-0002: フロントエンドで Effect 4 を採用する

## Status

Accepted

## Date

2026-10-02

## Context

フロントエンドでは、副作用、型付きのエラー、依存の管理、外部データの検証を扱う標準ライブラリとして Effect を使う（`docs/rules/frontend.md`）。まだ Effect を使ったコードは書いておらず、これから導入する段階である。

導入の直前の 2026-10-01 に、Effect v4 の最初の安定版である Effect 4.0 がリリースされた。v4 は内部を作り直したメジャーリリースで、次の特徴がある。

- `Context.Tag` が `Context.Service` に、`Effect.catchAll` が `Effect.catch` になるなど、多くの API の名前と使い方が v3 から変わった。
- `@effect/platform` など多くのパッケージが `effect` 本体に統合され、残った `@effect/*` パッケージも `effect` と同じバージョン番号で同時にリリースされる。
- `effect/http` など一部のモジュールは unstable とされ、マイナーリリースで破壊的変更が入る可能性がある。
- 長期サポートの方針が定められ、バグ修正は 2029 年 9 月、または 5.0 のリリースから 1 年後のいずれか遅い方まで提供される。

一方 v3 は、v4 の安定後もメンテナンスは続くが、機能追加は凍結されている。

このプロジェクトは、FP の考え方と Effect の導入によってバグを少なく運用できるかを検証し、結果によっては業務への導入を検討する実験である。そのため、検証の対象は、業務に導入する時点で使われるバージョンであることが望ましい。

## Options Considered

### Option 1: Effect 3 を採用する

- 概要: 機能追加が凍結された v3 系の最新版を使う。
- 利点: ドキュメント、記事、質問への回答などの情報が豊富で、AI によるレビューの提案も v3 の知識に基づくものが多い。API が安定している。
- 欠点: 機能追加が凍結されたバージョンで新規プロジェクトを始めることになり、いずれ v4 への移行が必要になる。検証の結果を業務に持ち込む時点では、v4 との違いを改めて評価する必要がある。

### Option 2: Effect 4 を採用する

- 概要: 2026-10-01 にリリースされた v4 系を使う。
- 利点: 長期サポートの対象であり、将来のメジャーバージョンへの移行まで数年の余裕がある。v3 からの移行コストが発生しない。まだ Effect のコードがないため、採用のコストが最も小さいタイミングである。検証の結果を、そのまま業務導入の判断材料にできる。
- 欠点: リリース直後で、情報の多くがまだ v3 を前提にしている。AI によるレビューで v3 の書き方を提案される可能性が高い。unstable なモジュールはマイナーリリースで変更が入る可能性がある。TypeScript 7 向けの Effect の言語サービス（`@effect/tsgo`）はアルファ版である。

## Decision

Option 2 を採用し、フロントエンドで Effect 4 を使う。

`docs/rules/frontend.md` のコード例とルールを Effect 4 の API に合わせて更新し、v3 と v4 で変わった主な API の対応表を載せる。unstable なモジュールは、`Layer` によるサービスの実装の中だけで使う。

### Tradeoffs

長期サポートのあるバージョンで検証できることと、将来の移行コストがないことを得る代わりに、リリース直後のバージョンを使うことによる情報の少なさと、unstable なモジュールの変更に追従するコストを受け入れる。情報の少なさは、ルールに v4 の書き方と v3 との違いを明記することで補う。

### Confidence

Medium

v4 の採用自体は、検証の目的と長期サポートの方針から妥当だと考える。ただし、リリース直後であり、実際に使ったときの不具合や周辺ツールの成熟度は未知である。導入後 3 か月を目安に見直し、v4 の不具合や周辺ツールの不足によって開発が止まる事態が繰り返し起きていれば、v3 への切り替えを再検討する。

## Consequences

### Positive

- 長期サポートのあるバージョンで検証でき、結果をそのまま業務導入の判断に使える。
- v3 から v4 への移行作業が発生しない。
- パッケージが `effect` 本体に統合され、依存の管理が単純になる。

### Negative

- v4 の情報が少なく、問題の調べ方が公式ドキュメントとソースコードに偏る。
- AI によるレビューで v3 の API を提案される可能性があり、レビュー結果を v4 の API と照らし合わせる手間がかかる。
- unstable なモジュールの破壊的変更に、マイナーリリースのたびに追従する必要がある。

## Compliance

- `frontend/package.json` で `effect` と `@effect/*` のバージョンを完全に固定し、すべて同じバージョンにする。Pull Request のレビューで、バージョンがずれていないことを確認する。
- `docs/rules/frontend.md` の「Effect Version」の節に v3 と v4 の対応表を置き、レビュー時に v3 の API が使われていないことを確認する。AI にレビューさせる際も、この節を参照させる。
- unstable なモジュール（`effect/http` など）の import が、サービスの実装以外に現れていないことをレビューで確認する。
- 導入後 3 か月を目安に、次の点を振り返る。
  - v4 の不具合や情報不足によって、作業が止まった回数と時間。
  - unstable なモジュールの変更への追従にかかった時間。
