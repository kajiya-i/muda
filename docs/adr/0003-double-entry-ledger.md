# ADR-0003: お金の動きを複式の台帳として記録する

## Status

Superseded by [ADR-0005](0005-multi-currency-ledger.md)

## Date

2026-10-02

## Context

このサービスの目的は、家族の購入申請に基づくお金の流れを記録し、可視化することである。お金の記録方式は、残高の正しさ、記録の追跡しやすさ、将来の機能追加のしやすさを左右し、データが蓄積した後に変更するのは難しい。

お金の記録には、次の要件がある。

- R1: 入金（家計にお金を入れる）、家計払い（家計から支払う）、立替（メンバーが自分のお金で支払う）、精算（家計からメンバーに立替分を返す）の 4 種類のお金の動きを記録する。
- R2: 家計残高と、メンバーごとの未精算額（家計がそのメンバーに返すべき金額）の 2 種類の残高を表示する。
- R3: 家計残高を超える支払いは、承認者が明示的に承認した場合を除いて禁止する。
- R4: 一度記録したお金の動きは変更・削除しない。訂正は打ち消しの記録を追加して行う。
- R5: 月別、カテゴリ別、メンバー別に支出を集計する。
- R6: 各お金の動きが、どの申請に基づくものかを辿れる。
- R7: 小遣い、返品・返金など、新しい種類のお金の動きを後から追加できる。

カテゴリは、あらかじめ用意した既定のカテゴリに加えて、家族が自由に追加・変更できる。

この ADR では、お金の動きの記録の形と、残高の求め方を決める。申請の状態の永続化、金額の表現、データベースの選定は、別の ADR で決める。

## Options Considered

### Option 1: 残高を直接更新する

- 概要: 家計やメンバーごとに残高を保存し、お金が動くたびにその値を書き換える。
- 利点: 実装が単純で、残高の取得が速い。
- 欠点: 書き換えた時点で過去の値が失われ、R4 と R6 を満たせない。残高が正しいかを後から検証できない。

### Option 2: 単式の取引ログ

- 概要: お金の動きを、種類、金額、メンバー、カテゴリ、申請への参照を持つ 1 行として、追記専用で記録する。残高は、ログを種類ごとの符号のルールで集計して求める。
- 利点: 構造が単純で理解しやすい。R4 と R6 を満たせる。
- 欠点: 「立替は家計残高に影響せず、未精算額を増やす」といった知識が、残高を求める処理の中に種類ごとの分岐として散らばる。新しい種類を追加するたびに、すべての集計の処理を見直す必要がある（R7）。記録が誤っていてもお金の総量の整合性を構造的に検出できない。

### Option 3: 複式の台帳

- 概要: 勘定を用意し、1 つのお金の動きを、合計が 0 になる 2 つ以上の記録（仕訳）で表す。各勘定の残高は、その勘定への記録の合計として求める。
- 利点: すべての取引で記録の合計が 0 になるという制約により、お金が消えたり増えたりする誤りを、取引を作る段階で検出できる。お金の動きの種類ごとの知識が「どの勘定からどの勘定へ動くか」として 1 か所にまとまり、残高を求める処理は種類が増えても変わらない（R7）。
- 欠点: 勘定と仕訳の概念を理解する必要がある。記録の行数が単式のおよそ 2 倍になる。

## Decision

Option 3 を採用し、お金の動きを複式の台帳として記録する。複雑さを抑えるため、次のように最小限の形で運用する。

### 勘定

勘定は次の 4 種類とする。

| 勘定 | 意味 |
|---|---|
| 家計 | 家計にあるお金 |
| 未精算 | 家計がそのメンバーに返すべきお金。メンバーごとに 1 つ持つ |
| 支出 | 使われたお金 |
| 拠出 | 家計の外から入ってきたお金 |

### 記録の表し方

- 会計の専門用語（借方・貸方、資産・負債などの分類）は使わず、符号付きの金額で表す。プラスはその勘定にお金が入ったこと、マイナスは出たことを表す。
- 1 つの取引に属する記録の金額の合計は、常に 0 でなければならない。
- 取引は、それを生じさせた申請への参照を持つ。

4 種類のお金の動きは、次の仕訳で表す。

| お金の動き | 記録 |
|---|---|
| 入金 | 家計 +、拠出 − |
| 家計払い | 支出 +、家計 − |
| 立替 | 支出 +、未精算（立て替えたメンバー）− |
| 精算 | 未精算（精算を受けるメンバー）+、家計 − |

### カテゴリ

カテゴリは勘定にせず、支出の勘定への記録の属性として持つ。家族がカテゴリを追加・変更しても、勘定の構成は変わらない。記録ごとにカテゴリを持つことで、将来 1 つの購入を複数のカテゴリに分けて記録できる。

### 残高

残高は保存せず、記録から毎回導出する。

### 訂正

記録を変更・削除せず、誤った取引を打ち消す反対の符号の取引を追加して訂正する。

### Tradeoffs

お金の総量の整合性を構造的に保証できることと、新しい種類のお金の動きを残高の計算を変えずに追加できることを得る代わりに、勘定と仕訳の概念を学ぶコストと、記録の行数の増加を受け入れる。学習のコストは、勘定を 4 種類に絞り、専門用語を使わず符号付きの金額で表すことで抑える。

### Confidence

High

複式の台帳は、お金を扱うシステムで長く使われてきた確立した方式である。今回の要件のうち、単式の取引ログに対する欠点は学習のコストだけであり、勘定を最小限に絞ることでそのコストも抑えられる。

## Consequences

### Positive

- 取引ごとに記録の合計が 0 であることを検証することで、お金が消えたり増えたりする誤りを構造的に防げる。
- 残高は勘定ごとの記録の合計で求まり、お金の動きの種類が増えても残高を求める処理は変わらない。
- 残高を保存しないため、保存した残高と記録がずれる誤りが起きない。
- 記録を変更しないため、任意の時点の残高を再現でき、すべてのお金の動きを申請まで辿れる。
- 残高を求める処理が、記録だけを入力とする純粋な関数になり、データベースなしでテストできる。

### Negative

- 勘定と仕訳の概念を理解する必要がある。
- 記録の行数が単式のおよそ 2 倍になる。
- 残高を毎回導出するため、記録が大きく増えた場合は性能の対策（記録から作るスナップショットなど）が必要になる。家庭内の利用では当面問題にならない見込みである。
- 残高超過の判定（R3）は「残高を求める、判定する、記録を追加する」の間に別の支払いが割り込むと正しく働かないため、データベースのトランザクションによる並行性の制御が必要になる。具体的な方法は永続化の方式の ADR で決める。

## Compliance

- 取引を表すドメインの型は、コンストラクタで記録の合計が 0 であることを検証し、合計が 0 でない取引を作れないようにする（`docs/rules/backend.md` §7）。
- 残高を求める処理は純粋な関数とし、4 種類のお金の動きそれぞれについて単体テストを書く。
- 台帳の記録を更新・削除するコードがないことを、コードレビューで確認する。データベースでの強制方法は永続化の方式の ADR で決める。
- 残高を保存する列やテーブルが追加されていないことを、コードレビューで確認する。
- MVP の後に、小遣いや返品などの新しい種類のお金の動きを追加する際、残高を求める処理を変更せずに済んだかを記録し、この判断の妥当性を評価する。
